# Durable internal activity

The production execution Durable Object runs a bounded deterministic assessment every 60 seconds once bootstrapped. The existing Worker's five-minute cron bootstraps that single production object and recovers a missing alarm. Browser connections, visibility, SSE and UI timers do not keep the loop alive. Cloudflare may evict the process between events; persisted alarms wake it again. This is scheduled continuity, not a permanently resident CPU or a guarantee against platform outages.

Each wake reads only statuses and hashes of opaque IDs from at most 64 recent turns and the existing persisted provider admission projection. It uses the canonical objective planner to build candidate plans when those observations change. Duplicate alarm deliveries and unchanged snapshots do not count as new builds. A hash of the recent turn IDs/statuses detects new work even when aggregate counts stay the same; raw IDs and content are not retained in planning artifacts. It retains at most 64 candidate artifacts, records the current source SHA, and never invokes a model, renews provider admission, sends connector actions, commits code, promotes a model or approves its own candidate.

Pause and resume use the existing signed owner bridge. A persisted owner pause survives cron bootstrap, alarm delivery, eviction and source updates. Public callers cannot access these controls by supplying internal headers. Both control payload shape and identity are validated before mutation. Source changes reset current-source observations and candidate counters without importing earlier candidates as authority.

The UI shows a background status on every view and details/controls in Advanced. It requires a fresh observation matching the published source SHA and Cloudflare durable storage. Missing evidence is unverified, missed wakes are delayed, pauses stay paused, and an invalid internal observation is held with another bounded wake scheduled. It displays plan counts and wake times, not private reasoning or conversation content. Polling is serial and pauses when hidden; the backend schedule continues.

The loop creates internal planning artifacts. Existing sovereign evolution and provider execution remain separately gated; an active heartbeat does not prove code builds, model cognition, learning promotion or real external execution. Runtime readiness and provider admission are separate observations.

References: [Cloudflare Durable Object alarms](https://developers.cloudflare.com/durable-objects/api/alarms/) document persisted scheduling, at-least-once delivery and retries. Context7 was used to verify the current scheduling contract. Tests cover persisted wakes, retry idempotency, owner pause/resume, source transitions, bounded/private-field validation, platform alarm execution, public spoof rejection, and UI observation/rendering. Platform billing and verified deployment remain under the existing hard-zero workflow; no new credential or provider is added.


## Verified-main publication and cockpit evidence

A merge performed with GitHub's repository token suppresses ordinary push workflows, including Pages builds. Mahoraga's trusted Autonomous Integration workflow therefore writes an immutable exact-merge publication receipt, uploads it to that source run, and dispatches `Verify Mahoraga` on the merged `main` SHA. After the Ubuntu lane completes its normal repository verification, it boundedly waits for the exact Autonomous Integration source run to reach terminal `completed/success`, then revalidates that run, repository, receipt artifact, merged SHA, current `main`, and the exact Verify run ID that the source workflow dispatched. It then emits a normalized `verified-main-publication-v1` artifact bound to that Verify run. Downstream `workflow_run` publication cannot start until the complete Verify workflow, including the Windows lane, has finished successfully.

Owner-triggered canonical verification and bot `push` verification keep their existing publication path. Bot `workflow_dispatch` publication is different: `github-actions[bot]` identity alone is not authority. Pages, staged release, and canonical Cloudflare publication must fetch the normalized Verify artifact and the bounded TypeScript validator must bind it to the same Verify run ID and exact merged SHA before any publication mutation proceeds. Missing, duplicated, expired, malformed, foreign-run, or stale receipts fail closed.

All lanes still reject fork/feature/PR/failed verification and pin checkout to the verified run's `head_sha`. Pages records that SHA in health metadata and checks authoritative main before building and again before deployment. Cloudflare preserves its exact-main check, independent Free billing attestation, provider admission and live acceptance gates. Stale source fails closed; neither a heartbeat nor a successful static build replaces runtime acceptance.

The cockpit explains the one-minute assessment cadence, five-minute schedule recovery, persistent owner pause, and unverified/delayed observations. No connection is represented as proof of running work. Windows production remains unchanged at `3.6.0`.

References: [GitHub token workflow suppression](https://docs.github.com/en/actions/concepts/security/github_token), [workflow-run events and source context](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run), and [avoiding untrusted workflow checkout](https://docs.github.com/en/actions/reference/security/secure-use). Context7 and the repository's actual bot-dispatched verification receipt were checked for this handoff.
